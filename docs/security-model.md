# Security model of a migrated app (as built)

This page describes what the generator actually emits and enforces, read from
the code. It is the reference for security review: every claim names
the file that implements it, and the gaps the code does not close are listed
under [Threat model](#threat-model).

Scope: the deployed Catalyst project — one **Advanced I/O** function
`c2c_api` serving every endpoint, plus the generated browser client. The
migration toolchain itself (CLI, deploy credentials on your machine)
is out of scope.

Related pages: [deploy-functions.md](deploy-functions.md) (function layout,
principal model for v1), [blueprints.md](blueprints.md) (workflow port).

## Principals

- The only caller identity is the **signed-in Catalyst Authentication app
  user**, read with user scope on every request:
  `sdk.initialize(req).userManagement().getCurrentUser()`. A project
  collaborator who is not an app user, or a request with no session, has no
  current user and is refused. Implemented in
  [`packages/deploy/fn/c2c-principal.mjs`](../packages/deploy/fn/c2c-principal.mjs).
- The user's Catalyst role maps to a Creator profile **only through
  `principal-map.json`**, written at deploy time
  (`App Administrator` → `Administrator`, `App User` → `User`, plus one entry
  per role the apply plan creates). A role is never promoted by name; an
  unmapped role has no profile and is refused. The Creator role is not set:
  Catalyst roles are not Creator roles. Role map merge and built-in
  precedence: [`packages/deploy/src/function-dir.ts`](../packages/deploy/src/function-dir.ts)
  (`DEFAULT_ROLE_MAP`, `functionDir`).
- The handler sees `{ profile, userId, loginUser? }`. `userId` is the Catalyst
  user id; `loginUser` is the user's email, used as the Creator `Added_User`
  owner value and to bind report record filters. A caller cannot set
  `req.user`: the entry resolves the principal itself before any handler runs
  ([`packages/deploy/fn/index.js`](../packages/deploy/fn/index.js)), and
  generated handlers accept it only from `req.user` / `req.catalyst.user`
  (`principalFromRequest` in
  [`packages/shims/src/access.ts`](../packages/shims/src/access.ts) — body,
  query, and headers are never a principal).
- Profile → Catalyst role planning, including the anti-escalation fold (a
  Creator profile that spells a built-in role becomes `Creator <name>` and
  clones `App User`, so an invite can never land on the built-in's grants):
  [`packages/auth/src/plan.ts`](../packages/auth/src/plan.ts). Public signup
  stays off; hosted and embedded login are both planned on.
- Data-hierarchy roles become Catalyst roles but share **no records up the
  hierarchy**: without View All a user sees only their own rows there. Listed
  per app in `migration-report.json` (`securityFidelity` in
  [`packages/deluge/src/generate.ts`](../packages/deluge/src/generate.ts)).

## Route authentication and authorization (server-side)

Every route below runs behind the entry gate in
[`packages/deploy/fn/index.js`](../packages/deploy/fn/index.js): unknown path
→ 404, wrong method → 405, body over 1 MiB → 413, non-JSON body → 400, then
principal resolution → **401 `{ error: "sign in required" }`** before any
handler loads. A posted `record` is re-typed by column type first (a wrongly
typed value is a 400 naming the field). The datastore handle is the
`zcatalyst-sdk` adapter at **admin scope**, scoped to the request; whether a
handler writes at all is decided by `c2c-deploy.json` mode (or
`C2C_DEPLOY_MODE`). Handler failures map through
[`packages/shims/src/store-errors.ts`](../packages/shims/src/store-errors.ts);
anything unmapped replies `err.status` or 500 `"request failed"`.

Per route (all `POST` except lookups):

- `POST /forms/<Form>/submit` and edit submit — form submit handlers
  (generated by [`packages/deluge/src/generate.ts`](../packages/deluge/src/generate.ts)):
  hidden form → 403; unauthenticated → 401; `authorizeWrite` for the profile,
  form, values, and op (insert vs update from `body.ROWID`, never `body.op`);
  system columns (`Added_User`, `Added_Time`, …) are set by the server, never
  copied from the client; on edit the stored row is loaded under the caller's
  modify scope first. Write-rule refusals and store errors map to 400/409/422
  with caller-safe messages; access denials map to 403; anything else is 500.
  The reply carries `projectReadable` values only (see below).
- `POST /forms/<Form>/record` — single-row read for the edit screen:
  principal + `authorizeRead` with `modify` intent, so a row the caller may
  read but not modify is refused here.
- `POST /reports/<Report>` — report reads: `authorizeRead` scope, i.e. the
  caller's profile grant **plus** the report record filters of reports they
  can view, plus the owner restriction. An unmigrated filter is a closed gate
  (reads refused for that profile), never an open one. Lookup display columns
  resolve through the same scoped parent read.
- `GET /lookups/:form/:field` — lookup options: `authorizeRead` on the parent
  form and readability of the display field itself; hidden fields are not
  returned. Paging comes from the query string only (a GET has no body to
  trust) and is validated server-side.
- `POST /uploads/:form/:field` and `POST /files/:form/:field` — see
  [File uploads](#file-uploads).
- `POST /flows/<machine>/{approve,reject,transition}` — state machines: gate
  order is hidden form (403), authenticated profile (401), then approver and
  status. Live transitions require `body.ROWID` (else 422) and **re-read the
  stored row under the caller's scoped read** — a row invisible to the caller
  denies with `"record is not visible to this caller"`. The transition is
  validated against the **stored** stage, never a client-supplied stage;
  `body.status` only picks among valid candidates. Transition criteria that
  cannot be evaluated stay closed gates. Approver check and owner semantics:
  see [Blueprint owners](#blueprint-owners) below. The stage write goes
  through `datastore.writeRow` and deliberately does **not** need the caller
  edit grant the form write would require (stated in the generated banner).
  History rows record `Actor` as the caller's login, user id, or profile.
- `POST /admin/smoke` — the in-browser smoke endpoint: 401 without a
  principal, **403 unless the principal's profile case-insensitively matches
  an Administrator profile** of the app
  ([`packages/ui/src/generate.ts`](../packages/ui/src/generate.ts), smoke
  stub). Its `status` op reveals only mode and form count.
- Prefetch (client field-rule/slot data): carries the same gate as the
  function route it belongs to; `authorizeRead` is shared by server handlers
  and the prefetch path, so a prefetch never returns a row or field the
  caller's profile could not read
  ([`packages/shims/src/access.ts`](../packages/shims/src/access.ts) header,
  prefetch note in
  [`packages/deluge/src/generate.ts`](../packages/deluge/src/generate.ts)).
- Custom workflow actions on reports: the caller must pass `authorizeRead`
  for the report form before anything runs (action stub banner in
  [`packages/ui/src/generate.ts`](../packages/ui/src/generate.ts)).

## Record, field, and stage rules

The policy object is `functions/access-policy.json`, built from the export's
profiles, module permissions, reports, share settings, and menu sections by
`buildAccessPolicy` in
[`packages/deluge/src/generate.ts`](../packages/deluge/src/generate.ts) and
enforced by [`packages/shims/src/access.ts`](../packages/shims/src/access.ts):

- **Form grants** per profile: `fields` (readable subset; absent = all, empty
  = none), `recordFilter` (OR of the viewed reports' filters, with
  `zoho.loginuser` binds resolved from the principal at read time — never
  from the request), `write`/`create`/`edit`/`delete` bits (delete is
  separate; write does not imply it), `writable` (writable subset; hidden
  fields are never included), `read: false` (add-only: no row or field may
  be read), `ownerScope: 'view' | 'modify'` (owner = row `Added_User` matched
  against the principal's login user; without a login user the read is
  refused).
- **Writes are reject, not drop, at every depth.** Unknown keys, hidden or
  read-only fields, system columns (`ROWID`, `CREATORID`, timestamps,
  `c2c_source_id`, `Added_User`, `Modified_User`, `Owner` in any case — with
  the single exception of an exact `Owner` key where the form has an editable
  field named `Owner`), lookup objects with keys other than `id`/`label`,
  file values other than `{ key }`, and nested objects at scalar positions
  all throw `RecordAccessError` (→ 403). Write schemas additionally carry
  `readonlyFields` (formula, autonumber, and the same).
- **Reply projection** (`projectReadable`): after a write the caller sees
  only the grant's readable fields plus system columns; an add-only grant
  sees only the keys it submitted plus the row id. Values a script or stored
  row added to a hidden field never reach the reply.
- **Roles allow-list**: a principal role outside `policy.roles` is denied.
- **Hidden menu sections**: forms, reports, and pages that appear only in a
  hidden section land in `policy.hidden`; direct navigation is denied (403)
  even when the profile could otherwise read them — the server-side denial
  is confirmed in every generated handler (`isHidden` check). The React
  client has no routing gate for hidden targets: `parseRoute`
  (`ui-react/template/lib/c2c-ui/runtime/router.ts`) maps
  `#/form|report|page/<name>` unconditionally, and `reactAppSpec`
  ([`packages/ui-react/src/generate.ts`](../packages/ui-react/src/generate.ts)
  `:182`) only drops hidden sections from the nav — their screens still
  generate, so a direct hash navigation renders the screen and each call
  then fails server-side with 403. The vanilla client probes the gate
  endpoint and paints `This page is not available.` on 401/403
  (`client-runtime.js` hidden-target probe; see
  [Client behavior](#client-behavior-on-401403)).
- **PII/ePHI flags**: `PIIAccess: false` / `ePHIAccess: false` on a profile
  are **not enforced** — personal-data fields are not hidden by them
  (`securityFidelity`, same file). Unmodelled module flags (Tab, export,
  import, comment, report-builder) are listed, not enforced.

### Blueprint owners

- A transition's approvers resolve to user, role, profile, or form-field
  kinds (`resolveApprovers`). Matching is against the principal: user values
  match login or user id (case-insensitive), role against the principal role,
  profile against the principal profile, and a field approver reads the
  record field the `.ds` named and matches its users value(s) against the
  caller.
- A form-field approver on a field that is not a users field, and a
  reporting-level approver, are **unsupported and deny** with that reason —
  counted in `migration-report.json`, never silently skipped. A transition
  with no approvers is open to any caller that passes the other gates.
- For approvals, the newest submit history row for the record names its
  submitter; the machine's own history-table read does not need the caller to
  hold a grant on that table.

### During-phase fields and stage-hidden fields

- Every `transition criteria` property — on the transition or inside any
  phase, in any letter case — gates the transition at runtime; the scripts
  AND. A criterion that cannot be translated, references an unknown field or
  function, or produced no verdict becomes a **closed gate** (`return false`
  / `deny(...)`) plus a migration todo.
- Phase Deluge bodies become the transition's run scripts. Stage and `start`
  settings blocks, non-criteria transition properties, and phase properties
  that are not `transition criteria` are **not translated into field rules**;
  they become migration todos (source-UI layout metadata, never silently
  dropped).
- Per-stage field visibility / editability from the Creator blueprint UI
  (e.g. "this field is hidden/editable during phase X") has **no server-side
  field-rule counterpart** in the generated code: the server enforces the
  profile field grants, the transition criteria, and the approver/status
  gates above — not a per-stage widget mask. Confirmed absent on the client
  too: no `stage`-keyed field mask exists in the React template, the vanilla
  runtime, or the shims (zero hits for stage/phase field-visibility
  constructs under `packages/ui-react/template`, `packages/shims/src`,
  `packages/ui/src`).
- Creator client field rules (show/hide/disable on value change): the
  **vanilla** client implements them — `fieldRuleSource`
  ([`packages/deluge/src/generate.ts`](../packages/deluge/src/generate.ts)
  `:1185-1200`) emits rule actions into `client/handlers/<form>/<event>.mjs`,
  which the UI ships as `slate/assets/handlers/*.js`
  ([`packages/ui/src/generate.ts`](../packages/ui/src/generate.ts) `:68-72`)
  and runs via `clientActions()` returning show/hide/enable/disable/clear
  ops. The **React** client does not implement them — `packages/ui-react`
  has no handler/clientActions wiring. Server-side enforcement of field
  rules: none; hidden-by-profile fields are the enforced subset.

## Public forms

There are none. The generator emits **no unauthenticated route**: the
function entry returns 401 before any handler runs, and every generated
handler repeats a principal check (401) plus its own gate. No
`public`/`skipAuth`/`allowAnonymous` bypass exists in the generator, the
entry, or the policy. Public signup is planned off (`public_signup: false`
in [`packages/auth/src/plan.ts`](../packages/auth/src/plan.ts)); enabling it
is a manual action in the Catalyst console, outside the generated code.

## File uploads

- Flow: the browser `POST`s `{ filename, contentType, sha256 }` to
  `/uploads/:form/:field`, gets a signed Stratus PUT URL, PUTs the bytes
  with the stated Content-Type, then submits the returned `{ key }` as the
  field value. Submit-time `authorizeWrite` accepts **only** `{ key }` for a
  file/image/audio/video/signature field.
- Upload authorization: hidden form → 403; no principal → 401; then
  `authorizeWrite(access, principal, form, { [field]: null })` — the field
  must be writable for the caller's profile. Only fields listed in the
  generated `fileFields` are signed live (else 404); with no live file store
  configured the endpoint is a 500, never a silent success.
- Key shape `uploads/<form>/<field>/<sha256>/<name>`:
  `uploadObjectKey` in
  [`packages/shims/src/files.ts`](../packages/shims/src/files.ts) requires a
  64-hex sha256, link-name form/field segments, and a sanitized base name
  (path separators stripped, max 80 chars). Signed URLs live 600 s
  (`SIGNED_URL_TTL_SECONDS`).
- Download (`POST /files/:form/:field`, body `{ rowId }`): the row is read
  with the caller's read policy (record filter included), so a caller gets
  only files of rows it can see; **the key comes from the stored row, never
  from the request**; only listed file fields are signed.
- Explicit limits: the server **cannot verify the bytes hash before the
  bytes arrive** — the key only names them (stated in `files.ts`).
  Content-Type is validated only as a well-formed MIME token
  (`contentTypeOf`), defaulting to `application/octet-stream` — there is no
  per-field type allow-list and no per-file size cap in the reviewed code.
  Confirm the live Stratus bucket policy (managed in your console, outside
  this repo) carries any needed size/type restriction.

## Output encoding and sanitizing

- The React client renders values through JSX (escaped by default). The
  submit-error banner shows the server message as **text**, not HTML
  (`FormView` in
  [`packages/ui-react/template/lib/c2c-ui/form/FormView.tsx`](../packages/ui-react/template/lib/c2c-ui/form/FormView.tsx)).
- Rich text: `sanitizeHtml` in the rich-text editor
  ([`packages/ui-react/template/lib/c2c-ui/arc/components/rich-text-editor/rich-text-editor.tsx`](../packages/ui-react/template/lib/c2c-ui/arc/components/rich-text-editor/rich-text-editor.tsx))
  rebuilds pasted markup from an allow-list — script, style, iframe, object,
  embed, svg, media, form controls, and head elements are dropped, style
  attributes are not carried, and links keep only safe hrefs. Markdown-ish
  input is HTML-escaped before minimal markup is applied (`escapeHtml`).
  The `safeUrl` allow-list is `/^(https?:|mailto:|tel:|\/|#)/i`
  (`rich-text-editor.tsx:19`): http, https, mailto, tel, root-relative `/`,
  and fragment `#`. **Gap:** the bare `/` alternative also admits
  protocol-relative `//evil.test` URLs, and `fields.tsx:386` sets
  `win.location.href` with no scheme check.
- Static pages/snippets: `sanitizeSnippet` in
  [`packages/ui/src/pages.ts`](../packages/ui/src/pages.ts) parses with
  `DOMParser` and copies only safe nodes; generated `index.html` escapes
  interpolated values (`escapeText`); the smoke plan embedded in
  `public/c2c-config.js` escapes `</` so its JSON cannot close the script
  element
  ([`packages/ui/src/generate.ts`](../packages/ui/src/generate.ts),
  `slateConfigSource`).
- Server replies never carry Catalyst's raw error text (the rule in
  [`packages/shims/src/store-errors.ts`](../packages/shims/src/store-errors.ts));
  caller-safe messages name only the field/form. Deluge conversion errors may
  quote the offending value to the caller — that is Creator's own message
  class, passed through unchanged by design.
- The vanilla client's `innerHTML` sinks are escaped: all 22 `innerHTML`
  sites in `client-runtime.js` (e.g. `:741`, `:791`, `:3343-3405`, `:3455`,
  `:3690-3748`) write either static literals or template output that passes
  values through `escapeHtml` (`client-runtime.js:14`); user content enters
  via `sanitizeSnippet` (`:147`) or text nodes.

## Headers and transport

- Function replies set only `Content-Type: application/json`. No
  `Content-Security-Policy`, HSTS, `X-Frame-Options`, or CSRF-token header is
  emitted by the generated function or the generated `index.html` (no
  `helmet`/CSP/meta was found in the generator or template). Transport
  security, framing policy for the hosted app, and authorized domains are the
  Catalyst platform's and your console settings (the sign-in hint
  names Authentication › Whitelisting › iFrame explicitly).
- Session handling: the browser attaches the Catalyst Web SDK raw token as
  the `authorization` header (no prefix) and sends cookies on remote calls
  ([`packages/ui-react/template/lib/c2c-ui/runtime/api.ts`](../packages/ui-react/template/lib/c2c-ui/runtime/api.ts),
  same contract in the vanilla `apiCall`). The token is requested **after**
  the target URL is validated: `apiUrl` pins every call to the page origin
  or the configured API origin (https, or http only to exact loopback), so an
  absolute, protocol-relative, or non-web-scheme endpoint throws before any
  credential is attached. The sign-in return URL is same-origin-pinned the
  same way (`serviceUrl` in
  [`packages/ui-react/template/lib/c2c-ui/runtime/auth.tsx`](../packages/ui-react/template/lib/c2c-ui/runtime/auth.tsx)).
- CSRF posture is **undetermined**: `readBody` (`fn/index.js:166-188`)
  accepts any Content-Type and parses the body as JSON, so the only barrier
  to a cookie-only cross-site POST is whether the Catalyst gateway accepts
  cookie auth on `/server/c2c_api` at all — not determinable from this repo.
  Both clients authenticate with `authorization: <raw token>`, which a
  cross-site form cannot set. Refusing non-JSON writes with 415 is planned.

## Secrets

- The client bundle and `public/c2c-config.js` contain **no secrets**: API
  base URL, app time zone, the Catalyst Web SDK loader, the smoke plan (form
  / field / route names and canned fill values only), and the smoke project
  id — the generator comments that the id is an id, not a secret. The only
  `import.meta.env` read in the shipped template is the `PROD` check for
  service-worker registration.
- Server-side, from environment or `c2c-deploy.json` (never the client):
  `C2C_DEPLOY_MODE`, `C2C_APP_TIMEZONE`, `C2C_MAIL_FROM` (verified sender),
  `C2C_ZOHO_DC`, `C2C_STRATUS_BUCKET`, `C2C_OWNER_APPROVAL_TOKEN` (from env,
  never a file), `connections` map + `c2c-connections.mjs` credentials
  (live only), and `outboundHosts` — the only hosts a live connection-less
  outbound call may reach. A caller's `Idempotency-Key` header seeds
  downstream idempotency keys only.
- `access-policy.json` / `principal-map.json` are authorization data shipped
  inside the function directory (server-side), not to the browser.

## Logs (no PII)

- Mapped store errors log one structured line — code, table, field,
  request id — never Catalyst's text, record values, or secrets, and the
  caller gets the same request id with its safe message
  (`logStoreError` / `replyStoreError` in
  [`packages/shims/src/store-errors.ts`](../packages/shims/src/store-errors.ts)).
- The Deluge runtime transcript (record values, table names, ops) is a
  dry-run debug view only; no live reply carries it. URL/header/parameter
  and thrown-message masking lives in
  [`packages/shims/src/redact.ts`](../packages/shims/src/redact.ts).
- History writes intentionally store the actor's login/user id/profile and
  the submitter. The entry's double-send path (`send()` in `fn/index.js`,
  ~`:117-124`) logs `JSON.stringify(body)` — the intended reply body, which
  on error paths is the caller-safe `{error}` object — plus `err.stack`.
  `err.stack`'s first line is `err.message`, which **can embed a record
  value** for the pass-through message class named above (Deluge conversion
  errors quoting the offending value). The line never logs request bodies or
  headers; the residual leak is record values via a thrown message (known
  gap; logging only `err.name`/`err.code` is planned).

## Client behavior on 401/403

- React: `AuthGate` renders only for a signed-in user when the Catalyst Web
  SDK is present (otherwise the embedded sign-in frame); with no SDK (local
  preview) the app renders and **the API decides access**. There is **no
  re-login redirect or special 401/403 branch** in the React data path: a
  denied record load shows `The record could not be loaded.`; a denied submit
  shows the server's message or `The record was not saved.`; a denied report
  shows the error state (while 404/405/501 — route absent — render as an
  empty report, not an error).
- Vanilla client: routes in hidden menu sections are probed server-side
  before painting; 401/403 (or any failure) paints
  `This page is not available.` A failing lookup fill is tolerated
  (the select stays empty); the smoke page distinguishes 403 (needs an
  Administrator profile) from not-signed-in.
- Session-expiry mid-use is a **known gap**: neither client handles a
  401/403 after boot. React `AuthGate` checks `isUserAuthenticated` once at
  mount (`auth.tsx` ~`:47-57`) and `createApi().post` never branches on
  status (`api.ts:162-181`), so a mid-session 401 surfaces the raw
  `body.error` in the FormView banner. Vanilla `apiCall` returns the
  Response unexamined (`client-runtime.js` ~`:2226`); call sites show raw
  "sign in required", blank edit forms, or silently empty selects. No draft
  save, no retry, no access-denied screen.

## Threat model

What a migrated app defends against (all server-side, all in the request
path):

- Unauthenticated access: every endpoint requires a Catalyst session (401
  at the entry, re-checked per handler).
- Cross-profile access: profile/role mapping is deploy-time data, never
  client input; unknown roles, missing profiles, and missing form grants
  deny; untranslatable record filters deny reads rather than opening them.
- Direct-object and field access: row reads are re-scoped to the caller's
  grant + record filter + owner scope; writes reject unknown/hidden/
  read-only/system keys instead of dropping them; replies are projected to
  readable fields.
- Parameter tampering: ownership columns are server-set; edits load the
  stored row under modify scope; transitions validate against the stored
  stage with the row re-read; download keys come from stored rows; upload
  references must be server-issued `{ key }` shapes.
- Privilege creep by naming: profile names that fold onto Catalyst built-in
  roles are renamed to `Creator <name>` and clone `App User`.
- Token theft via redirect/origin confusion: same-origin sign-in return and
  page-or-configured-API-origin request pinning, checked before the token is
  attached.
- Stored/reflected XSS via content: allow-list sanitizers on rich text and
  snippets, escaped interpolation in generated HTML/config, no raw
  platform error text to the caller.
- Secret sprawl: credentials live in server env / console config, never in
  the client bundle or logs; log lines are structured and value-free.

What it explicitly does **not** defend against:

- **Direct Data Store access.** Catalyst table permissions are per table
  and role with no field or row rule: a role given direct table access from
  a client reads past hidden/read-only fields, record filters, owner scope,
  and add-only grants. These hold **only through `c2c_api`** — the
  generated client reads and writes only through `c2c_api`, but the boundary
  is the platform permission table, and the per-app gap list is in
  `migration-report.json` (`securityFidelity.notEnforced`). A review
  should confirm the deployed permission rows match the plan.
- Platform-console misconfiguration: authorized domains, iFrame
  whitelisting, public signup, Stratus bucket policy, and connection
  credentials are managed in the console, outside the generated code.
- Creator semantics the port does not express: role-hierarchy sharing,
  `PIIAccess`/`ePHIAccess` flags, per-stage widget masks, reporting-level
  approvers, and unmodelled module flags (listed in `migration-report.json`,
  not enforced).
- Imported-row ownership: migrated rows keep their Creator `Added_User`, so
  a user owns an imported row only when that value equals their login.
- Post-write script failure: if a script throws after the row write, the
  row stays (Creator rollback semantics are unverified and not implemented).
- Malicious customization or app administrator: browser customizations
  (`beforeSubmit`/`afterSubmit`, slots) and anyone with deploy/console
  access operate inside the trust boundary by design.
- Availability abuse: the 1 MiB body cap and ZCQL paging caps bound the
  cheapest floods; there is no broader rate limiting in the generated code.

Known gaps (each a confirmed defect in the port, not unexpressed Creator
semantics):

- **Known gap — client 401/403 handling:** no draft save, no re-login, no
  access-denied screen in either client.
- **Known gap — unmapped role gets 401, not 403:** a signed-in user whose
  role maps to no profile (including the default `App User`, which no
  migrated app carries a `User` profile for) is refused 401 rather than a
  403 naming the cause — and would loop sign-in once a re-login redirect
  exists.
- **Known gap — hidden-field oracle via report `filter`/`sort`:**
  `authorizeRead` (`packages/ui/src/generate.ts:1373`) does not check
  criteria fields, so a caller can probe hidden columns through
  filter/sort error or timing.
- **Known gap — no server-side picklist membership check:**
  `packages/shims/src/write-rules.ts` carries no choice rule, so an
  out-of-list value is stored.
- **Known gap — lookup target unchecked:** `screenLookup`
  (`packages/shims/src/access.ts:545`) validates shape only; the
  client-sent `label` is trusted and target existence/visibility is not
  verified.
- **Known gap — upload key overwrite:** a signed upload key derived from
  the caller's own sha256 can overwrite another row's file at the same
  path.
- **Known gap — `/admin/smoke` ships in production:** the smoke endpoint
  is always routed, and its marker field is user-writable.
- **Known gap — report grant not checked:** any report of a readable
  form is callable regardless of the profile's report grant.
- **Known gap — log hygiene:** record values can reach the double-send
  log line via a thrown message (see [Logs](#logs-no-pii)).
- **Known gap — URL scheme leftovers:** `safeUrl` admits
  protocol-relative `//` URLs and `fields.tsx` sets `location.href`
  unchecked (see [Output encoding](#output-encoding-and-sanitizing)).
