# Creator Enterprise Caps vs. Catalyst Limits

Code: `packages/deluge/src/schedules.ts` (scheduling plan, sweeper module, known gaps),
`packages/shims/src/long-work.ts` (asynchronous Job deferral, slice engine),
`packages/cli/src/precheck.ts` (static precheck analysis and cap risk warnings),
`packages/schema/src/limits.ts` (budgeted platform limits).
Related docs: `docs/job-scheduling.md`, `docs/large-data.md`.

This document maps Zoho Creator Enterprise plan caps to their corresponding Zoho Catalyst platform limits, identifies where Catalyst's runtime constraints are stricter than Creator's, and specifies the adapter patterns required to prevent migration failures.

Evidence tags: `[DOC]` is a public Zoho page, `[TESTED]` is a run against a Catalyst project, `[UNVERIFIED]` is not established. An `[UNVERIFIED]` sentence is context, not a fact.

## 1. Deluge Statement Limit (50,000 statements/action)

### Creator Enterprise Cap
- **Cap**: 50,000 Deluge statements per action on Enterprise plans (`[DOC]`, https://www.zoho.com/creator/pricing-comparison.html, row "Deluge execution statements").
  - Free: 5,000 statements (`[DOC]`, same page)
  - Standard: 10,000 statements (`[DOC]`, same page)
  - Professional: 20,000 statements (`[DOC]`, same page)
  - Enterprise: 50,000 statements (`[DOC]`, same page)
  - Blueprint change-stage and execute-transition functions: 50 statements (`[DOC]`, https://help.zoho.com/portal/en/kb/creator/developer-guide/limitations/articles/workflows-limitations)
- **Creator failure behavior** (`[UNVERIFIED]`): The error text `Number of statement execution limit exceed`, a full halt when that limit is crossed, and a partial-failure mode in form actions (the record commits with `code 3000 "Data Added Successfully"` while the `on success` script rolls back) were not found on a Creator help page. Keep them as operator context until a help page or a captured run confirms them. The same applies to schedule overruns: no primary page located describes a partial commit when a schedule exceeds its statement budget.

### Mapped Catalyst Limit
- **Statement counter**: No Catalyst functions page located publishes a statement-count cap. Documented bounds are execution time and configured memory (`[DOC]`, https://docs.catalyst.zoho.com/en/faq/serverless/ and https://docs.catalyst.zoho.com/en/cli/v1/working-with-functions/configure-function-memory/). An affirmative claim that Catalyst has no statement counter, or that "Node stops on time and memory, not statements", is `[UNVERIFIED]`.
- **Function execution time**:
  - **Basic I/O and Advanced I/O**: **30 seconds** (`[DOC]`, https://docs.catalyst.zoho.com/en/faq/serverless/: "The execution time limit for Basic I/O and Advanced I/O functions is 30 seconds."). `function.timeout_seconds` in `packages/schema/src/limits.ts` stores 30. The older execution-limits URL now 404s. Whether that cut is non-raisable, and whether the platform returns HTTP `408 EXECUTION_TIME_EXCEEDED`, stay as previously recorded behavior and were not re-checked against a live project in this pass (`[UNVERIFIED]` for the 408 text). AppSail sharing the same 30-second cut is `[DOC][TESTED]` in `docs/large-data.md`; the FAQ sentence above does not name AppSail.
  - **Job functions**: **15 minutes** (`[DOC]`, https://docs.catalyst.zoho.com/en/serverless/help/functions/job-functions/: `getMaxExecutionTimeMs()` is a constant of 15 minutes). The same FAQ gives Event and Cron functions 15 minutes. `job.timeout_minutes` in `packages/schema/src/limits.ts`.
- **Function memory**: Default **256 MB**, configurable from **128 MB to 512 MB** (`[DOC]`, https://docs.catalyst.zoho.com/en/cli/v1/working-with-functions/configure-function-memory/). The earlier "typically 256 MB or 512 MB" wording is not what that page says. A function-GET response field was not used as the source.
- **Authoritative number status**: The 30-second Basic/Advanced I/O limit and the 15-minute Job function limit are `[DOC]`. No published statement-count limit was located. That absence is `[UNVERIFIED]` as a guarantee that Catalyst never counts statements.

### Where Catalyst is Stricter & Migration Restructuring Required
- **Where Catalyst is stricter**: On the synchronous request path, Catalyst documents a 30-second Advanced I/O cut (`[DOC]`, FAQ above). A general Creator Deluge script timeout of 40 seconds was not found (`[UNVERIFIED]`). What is documented: `invokeurl` throws a socket timeout if the remote side takes more than 40 seconds (`[DOC]`, https://www.zoho.com/deluge/help/webhook/invokeurl-api-task.html), and Creator cloud functions in Node.js or Java are limited to 40 seconds (`[DOC]`, workflows-limitations page above). "Background workflows run even longer than 40 seconds" is `[UNVERIFIED]`. In Catalyst, HTTP request handlers, form submissions, and custom API endpoints generated by c2c run inside Advanced I/O functions under that documented 30-second cut.
- **Migration Restructuring**:
  - A Deluge script executing near the 50,000 statement cap—especially scripts containing nested loops, multi-table queries, external `invokeurl` HTTP requests, or `sendmail` iterations—risks exceeding Catalyst's 30-second wall-clock timeout if executed inline.
  - **Restructuring pattern**:
    1. Long work must be offloaded from the request path using `runOrDefer` (`packages/shims/src/long-work.ts`). The handler answers HTTP **202 Accepted** with `{ work_id, state, poll }` and a `Location: /c2c/work/<work_id>` header, enqueuing an asynchronous Job (`submitJob`).
    2. The Job function runs the execution in slices bounded by `JOB_SLICE_MS` (12 minutes, safely within the 15-minute Job function limit).
    3. State and cursors are checkpointed after each step; if additional work remains, the Job resubmits itself under the same `work_id` until completion.
    4. Client callers poll `/c2c/work/<work_id>` until status is `done` or `failed`.

## 2. Custom Schedules Quota (600 schedules/user/month)

### Creator Enterprise Cap
- **Cap**: custom-schedule **executions** per user per month (`[DOC]`, https://www.zoho.com/creator/pricing-comparison.html, row "Custom schedules"; https://www.zoho.com/creator/pricing.html).
  - Free: not offered (`[DOC]`)
  - Standard: 90 / user / month (`[DOC]`)
  - Professional: 300 / user / month (`[DOC]`)
  - Enterprise: 600 / user / month (`[DOC]`)
- The unit is executions, not definitions (`[DOC]`, https://help.zoho.com/portal/en/kb/creator/developer-guide/workflows/create-and-manage-schedules/articles/configure-schedule-to-run-on-a-date-field-value: "The number of custom schedules that can be executed per user per month depends on your Creator plan.").
- **Creator failure behavior**:
  - Pooling those per-user figures into one account total (for example 10 Enterprise users = 6,000) is arithmetic on the pricing row, not a sentence on the pricing page (`[UNVERIFIED]`).
  - Form schedules counting one execution per record per run: no primary page located. The pricing row is titled "Custom schedules" (`[UNVERIFIED]`).
  - Every schedule in the account stopping when the monthly quota is exhausted: no primary page located (`[UNVERIFIED]`).

### Mapped Catalyst Limit
- **Cron quota**: No Job Scheduling page located publishes a cron-count ceiling or a monthly execution quota. The honest status is **no published limit located** (`[UNVERIFIED]` if read as "Catalyst states there is no such limit"). Pages checked state a one-minute minimum and retry bounds, not a count or a monthly quota: https://docs.catalyst.zoho.com/en/job-scheduling/help/cron/key-concepts/ and https://docs.catalyst.zoho.com/en/job-scheduling/help/cron/benefits/. The deprecated CloudScale Cron page does say production cron execution has no upper limit, and development allows 500 executions per project per day (`[DOC]`, https://docs.catalyst.zoho.com/en/cloud-scale/help/cron/implementation/). That component is not Job Scheduling (https://docs.catalyst.zoho.com/en/announcements/2026/cron-sunset/) and does not set the quota for crons c2c generates.
- **Authoritative number status**: No published Job Scheduling numeric ceiling for cron count or monthly executions was located. That is not a documented promise of unlimited crons.
- **Catalyst Scheduling Mechanics**:
  - **Execution interval**: Minimum 1 minute between runs (`[DOC]`, https://docs.catalyst.zoho.com/en/job-scheduling/help/cron/key-concepts/).
  - **Cron types**: `CronExpression`, `Periodic`, `OneTime` (c2c generator names; Job Scheduling documents pre-defined and dynamic crons, one-time and recursive).
  - **Target**: Crons c2c emits target the Job function `c2c_jobs`.
  - **Job pool**: c2c creates one pool per application. The generator keeps pool names alphanumeric because hyphens and underscores are rejected.
  - **Form schedule sweeper**: No Job Scheduling page located describes a native record-date form scheduler (`[UNVERIFIED]` as an affirmative "Catalyst has none"). c2c translates form schedules into a single sweeper Job on a 5-minute Periodic cron (`SWEEP_PERIOD_MINUTES = 5`) targeting `functions/job/c2c-form-sweeper.mjs`.
  - **Sweeper Budget**: The sweeper stops after 4 minutes (`SWEEP_BUDGET_MINUTES = 4`) to prevent overlapping executions with the next 5-minute tick.

### Where Catalyst is Stricter & Migration Restructuring Required
- **Where Catalyst is more permissive**: No published Job Scheduling monthly execution quota was located (section above). This mapping does not claim that a sweep of thousands of records is guaranteed never to shut schedules down. Creator's account-wide stop is itself `[UNVERIFIED]`.
- **Where Catalyst is stricter / differs**:
  - **Execution granularity**: Form schedules fire on the first 5-minute sweep tick after their due time, so firing can lag by up to 5 minutes. A Creator trigger resolution of 1 minute is `[UNVERIFIED]`.
  - **Sweeper time budget**: Creator running each form-schedule record as its own execution is `[UNVERIFIED]` (same per-record claim as above). In the c2c mapping, all form schedules in the application share one sweeper execution bounded by the 4-minute budget the generator enforces.
  - **Restructuring pattern**:
    1. Form schedules page records through ZCQL in batches of 300 (`ROWID > cursor ORDER BY ROWID`).
    2. Checkpoints (`C2CJobCheckpoint`) record progress after every page.
    3. If an application contains numerous form schedules or tens of thousands of active records, a single sweep cannot exceed 4 minutes. Records not completed within 4 minutes are checkpointed and deferred to the next 5-minute window.
    4. Migration analysis must verify that record volumes per 5-minute interval fit within the sweeper's 4-minute processing window.

## 4. Adapter Honesty and Diagnostics

1. **`job-scheduling.json`**: Emitted by `packages/deluge/src/schedules.ts`. The `knownGaps` array explicitly carries both `creator-schedule-quota` and `deluge-statement-limit`, linking the Creator Enterprise limits to their respective Catalyst behavior and sources.
2. **`c2c precheck`**: Flags static migration risks:
   - `statement-limit-risk`: Warns on functions or workflow scripts with >= 5,000 Deluge statements. It names the Creator Enterprise cap of 50,000 statements/action (`[DOC]`) and the risk of exceeding Catalyst's documented 30 s Advanced I/O timeout. "Catalyst has no statement counter" stays `[UNVERIFIED]` (section 1).
   - `schedule-quota-risk`: Warns when the app defines >= 600 schedules (`app.workflows` schedule definitions). That count is a static definition-count proxy for Creator's 600 custom-schedule **executions** per user per month (`[DOC]`). It is not evidence that the per-user monthly execution quota has been or will be hit. The finding also names the 5-minute sweeper and its 4-minute budget.
