# Determinism

Generated output is a pure function of its input: two clean generations of the
same `.ds` export produce byte-identical trees. This is what lets a reviewer
diff regenerated output, lets CI prove nothing drifted, and lets the
migration targets in [docs/determinism-status.md](../determinism-status.md)
mean something.

## The rule

Generated bytes for a committed fixture change only with a reviewed reason,
stated in the pull request. A change that legitimately alters output
regenerates the committed evidence in the same pull request; an unexplained
manifest diff is a defect, not paperwork.

## The mechanisms

Three layers enforce it, all run offline:

1. **The codegen lint** — `packages/determinism/src/lint.ts`, run inside
   `npm test` (the test is `packages/determinism/test/determinism.test.ts`).
   It scans pipeline sources for the constructs that break determinism:
   clocks (`Date.now`, `new Date`), locale-dependent comparison
   (`localeCompare`), and iteration over unordered collections reaching
   generated bytes. A site that is genuinely safe carries a
   `// determinism-allow:` comment naming the reason on that line, or a
   `/* determinism-allow-file: … */` banner for a whole file. An unexplained
   finding fails the suite.
2. **Committed manifests** — one `<sha256>  <path>` line per generated file
   under `packages/determinism/test/manifests/<fixture>.sha256`, mirroring
   `fixtures/redistributable/`. `npm run determinism:check` regenerates and
   compares; `npm run determinism:update` rewrites them (the tool is
   `packages/determinism/src/manifests.ts`). A fixture without a manifest, or
   a manifest without a fixture, is drift. The suite also verifies the
   committed files are in the canonical form `renderManifest` emits.
3. **The determinism gate** — `tools/determinism-gate.sh`, run by
   `npm run check` and by CI (`.github/workflows/ci.yml`). It generates every
   committed fixture's full output tree twice, each run in a fresh process in
   its own clean directory, hashes every file, and fails on any difference.

## When your change alters generated bytes

1. Confirm the diff is intended — read the manifest diff, not just the test
   failure.
2. Run `npm run determinism:update` and commit the new manifests in the same
   pull request.
3. Say in the pull request why the bytes changed.

`docs/determinism-status.md` is a generated file too: refresh it with
`C2C_FIXTURES_DIR=<fixtures> npm run determinism:status` rather than editing
it by hand (the status test fails when it is stale and the local corpus is
present). The same applies to `docs/deluge-builtins.json` — see
[deluge-builtin.md](deluge-builtin.md).

## Rebasing a branch that carries regen commits

A regeneration commit must be the last commit of its pull request, and the
branch is rebased onto the main tip at the time it finishes — not the tip
it started from. Run `npm run det:rebase-regen` right before opening or
updating the pull request. The tool fetches `origin`, replays the branch's
commits onto `origin/main` while dropping every commit whose only changes
are generated files (the manifests, `docs/determinism-status.md`,
`docs/decimal-audit.md`, `docs/quality-gate.md`, `docs/coverage-gate.md`,
`docs/deluge-builtins.json` and `tests/ratchet/todo-kinds.json` — detected
by changed paths, not by subject), regenerates the artifacts, and commits
`Regenerate determinism manifests` last. It prints one summary line —
`det:rebase-regen: base=<sha> dropped=<n> regen=<sha|none>` — to paste
into the report; reviewers check that line against the diff.

A conflict on any non-generated path stops the run with the previous HEAD
restored: resolve it with a manual rebase, never by hand-editing around
the tool. The tool refuses a TODO-ratchet rise unless you pass
`--allow-increase "<reason>"`, and it never pushes.

## Known limits

`determinism:status --sites <file>` pins the output directory before the
gallery scan and writes through a child process that re-verifies the pinned
inode before creating and renaming its temp file. One residual race remains:
after the child's last directory check and before its `rename`, an active
racer could rename the pinned directory itself into the repo tree, and the
rename would still land there because it acts on the pinned inode (Node on
macOS has no `renameat`, so the check and the rename cannot be one syscall).
The window is microseconds and needs a racer already able to rename that
directory; closing it would need a platform file-system primitive Node does
not expose.
