# Slate PWA

This is the vanilla UI target. Generated UIs are moving to React: see `docs/react-target.md` (`c2c ui-react`).

The UI generator writes a static app for Zoho Catalyst Slate. It does not deploy, and it does not generate a native app. Native iOS and Android apps (and MDM) are not supported in this version (counted; on the roadmap); the installable client is this PWA.

## Framework

The client is vanilla ES modules plus a hash router in `packages/ui/src/client-runtime.js`. Preact and Lit were the other candidates. They were not used.

Slate serves every file with `cache-control: public, max-age=31536000`. A framework runtime would be another file that has to be content-hashed and loaded before a form can paint, and the screens are generated data (fields, reports, ZML), not a component tree we author by hand. The runtime is one module. The app model is another. Both are hashed. There is no second package to keep in step with Slate's cache.

## Cache

`index.html` and `sw.js` keep stable URLs. Every other asset is named with the first 10 hex characters of its SHA-256. Slate sends `cache-control: public, max-age=31536000` on every file and offers no per-file header control, and browsers do not honour `<meta>` cache directives for document caching — so `index.html` carries none, and nothing in the markup can stop the HTTP cache from holding a stale copy of it. What actually keeps a redeployed app fresh:

- The worker script is the update signal: `sw.js` embeds a hash of the `index.html` bytes plus the precache names, so an edit that touches only `index.html`, or one byte of a hashed asset, changes `sw.js`. An update check runs on every navigation to a controlled page (a soft update fires for every non-subresource request) and on `register()`, which the generated `pwa-register.js` calls on each page load. That check fetches `sw.js` with cache mode `no-cache` — the registration sets `updateViaCache` to `none` — so the year-long `max-age` on `sw.js` is never honoured there. Independently, a registration left unchecked for more than 24 hours is always revalidated.
- On install the worker precaches every entry, `index.html` included, through `cache.addAll` of `Request`s with `cache: 'reload'`, so a new worker cannot install a stale `index.html` out of the year-old HTTP cache.
- Once the worker controls the page, navigations — and any other fetch of `index.html` — are network-first: the shell is fetched with `cache: 'no-cache'`, so the year-fresh HTTP copy is never served without revalidation, and the cached shell is only the offline fallback. A successful response refreshes the cached shell. `c2c-config.js`, the other stable-URL file, gets the same treatment. Hashed assets are immutable and stay cache-first.
- On activate the worker deletes caches whose names start with `c2c-` and are not its own — previous versions of this app — and leaves foreign caches alone. `skipWaiting` plus `clients.claim()` hand control to the new worker as soon as it activates, so the next navigation is already on the new shell.

Residual risk: before any worker controls the page, a stale `index.html` can still be served straight from the HTTP cache — a first-ever visit, a browser with service workers disabled, or a page already open before its next navigation all sit in that window, and Slate's `max-age=31536000` gives it a worst case of a year. There is no header or markup a customer can set on Slate to shorten it. The mitigation is operational: a hard reload bypasses the HTTP cache, and under an installed worker any navigation converges to the fresh shell because the update check that navigation triggers lands the new `sw.js`.

`sw.js` stores only the shell: the precache list, `index.html` and `c2c-config.js`, which are the same bytes for every user. It never writes an API response to Cache Storage. A same-origin `GET` under `/server/`, or any other request outside the shell (an API read on a custom same-origin base, an old asset name), goes straight to the network, so one user's data is never answered to another user or to a signed-out page, and signing out leaves nothing user-specific in Cache Storage. Offline, the shell still loads, the page shows "Offline: data unavailable", and report reads show their error state with a Retry button. `sw.js` does not intercept `POST`, `PUT`, `PATCH`, or `DELETE`; a form submit needs a network. Every same-origin `/accounts/`, `/__catalyst/`, `/baas/` or `/server/` request — the embedded sign-in page, the SDK and the API — and every cross-origin request are never intercepted: a shell answer for `/accounts/…/signin` would show the app inside the sign-in frame. Hashed shell assets are cache-first. A cache write only ever runs for a `200` response, and a rejected write (a `206`, `Vary: *`, a full quota) never replaces the network response the page receives.

Offline API data is not available. Showing last-known data offline would need a cache keyed to the signed-in user, writes only for responses without `Cache-Control: no-store` or `private`, and a purge on sign-out and on any `401` or `403`; that is a possible later option, not current behaviour.

The installable-PWA files are runtime-neutral — `packages/ui/src/pwa.ts` emits `manifest.webmanifest`, the icons, `sw.js`, `pwa-register.js` and `_redirects` from a `{ name, themeColor, backgroundColor, iconRgb }` spec, so any shell can ship them. The manifest takes `theme_color` from the shell accent and `background_color` from the shell background token. Each icon draws the app initial(s) on the icon background colour inside the maskable safe zone, so one PNG serves `any maskable`. `pwa-register.js` is a plain script any shell page includes with `<script src defer>`; runtimes do not register the worker themselves. `_redirects` answers `/app` and `/app/*` with a `302` to `/`, then serves `index.html` for every other path. Slate applies the first rule that matches. A sign-in return can still bounce to the legacy `/app/` path, and a `200` rewrite there would keep `/app/` as the page URL: the shell's relative `./assets/…` URLs would resolve under `/app/` and load HTML. The app routes on the location hash, so the catch-all needs no deep-path logic.

`serviceWorker()` in `packages/ui/src/generate.ts` returns the same worker template (build tokens unfilled) for a shell that builds its own bundle. A React target reuses the PWA layer by adding:

- `sw.js` from `serviceWorker()`, with its bundler filling `@@cache@@`, `@@index@@` and `@@precache@@`, so it inherits the shell-only cache rule above.
- `pwa-register.js` from `pwaRegisterScript()` in its public files, loaded with `<script src defer>`, in place of its own registration; any registration it keeps must pass `updateViaCache: 'none'`.
- A web manifest with `id`, `start_url` and `scope` of `./`, plain icon paths (the `@@asset:` tokens in `pwaManifest()` are resolved only by `buildSlate`), and icons from `appIconPng()` at 192 and 512.
- A `_redirects` file from `slateRedirects()`.

## What is generated

- Forms, one screen per IR form. Widgets follow `docs/schema-mapping.md`. Mandatory, unique (server-side), regex, and max length become checks in the browser. Lookups call `GET /lookups/<form>/<field>` in pages of 300 rows, the measured ZCQL cap. Subforms are editable grids. The submit body omits read-only fields (autonumber, formula, and any other read-only widget). On edit, a visible field (including a composite part or subform cell) the user empties is cleared (sent as an empty string or null depending on type) so the stored value is overwritten; an invisible or unloaded value is never cleared. A subform row whose every field is empty is left out of the submit. An edit whose loaded record has no subform key does not post that subform, so the stored child rows stay. A file, image, or signature field cleared on edit causes the stored file reference to be cleared. File, image, audio, video, and signature fields are not JSON-encoded `File` objects. The client POSTs `{ filename, contentType }` to `POST /uploads/<form>/<field>` first. That dry run writes no bytes. It returns `reference: { key }`, and the submit value is exactly that object. `authorizeWrite` accepts `{ key }` for those fields and rejects a string, `{}`, or any extra key. The column stores `key`. An empty file input is omitted (unless explicitly cleared on edit).
- A record delete (`POST /forms/<form>/delete`) checks the profile delete grant, reads the row under the caller's modify scope (404 outside it — without `Modifyall` only a row the caller added), runs the `on delete`-scoped validates (a `cancel delete` answers 422 `refused` and the row stays), removes the row, then runs the `on delete` script and the delete-scoped `on success` modules. Those modules run after the commit: if one throws, the reply is 500 — or 403 on an access error — with `deleted: true`. The row is gone and is never restored, so a failed delete reply must be read with that flag, not assumed rolled back.
- Client handlers from the Deluge generator (`on load`, `on user input`, `on validate`) are copied into the PWA and called with a browser shim. The shim prefetches from the generated endpoint and then runs the handler. The prefetch URL is not the form-event server route. On load, on user input, click, and subform row events do not POST that route, so a server body on those events does not run; each one is counted in `migration-report.json` as `form-event-server-uninvoked`. `on success` is the submit URL when that endpoint exists. `on edit` is posted to `/forms/<form>/submit`. Whichever module owns that URL runs the same gate as the submit stub — hidden form, `op: "view"`, and `authorizeWrite` on the record, including subform rows — before the workflow script. `authorizeWrite` rejects a key that is not a writable field of that form or subform. It does not drop the key. Rejected names include any case of `ROWID`, `CREATORID`, `CREATEDTIME`/`Added_Time`, `MODIFIEDTIME`/`Modified_Time`, `c2c_source_id`, `added_user`, and `modified_user`. After that rejection the server sets `Added_User` and `Added_Time` on insert, and `Modified_User` and `Modified_Time` on update, before the workflow script. An update payload never carries those columns: the record's merged system values stay on the in-memory record for scripts and the reply, and are dropped before the store write, so an update leaves `Added_*` untouched. A client value never becomes those columns. On edit, and on add or edit when `body.ROWID` names a row, the server loads that row with the caller read policy and copies stored Added_User and Added_Time first. Add versus edit follows that ROWID, never `body.op`. Added User stores the Creator username (`zoho.loginuser`), not the email (`zoho.loginuserid`). Added Time and Modified Time are the application time zone (`C2C_APP_TIMEZONE`, otherwise the IR `time zone`). `Owner` is rejected unless that depth has an editable field named `Owner`, and then only the exact key `Owner` is accepted. A lookup value may contain only the exact keys `id` and `label`. An address or name value may contain only its known parts. Approval and blueprint endpoints, and custom-function POSTs, use the same order: hidden form, then the authenticated profile, then authorize. They re-read the record on the server (a dry run uses a documented placeholder) and do not trust a client record, previous row, or subform row. `body.status` must be the target of a transition whose `from` is the record's current stage. The dry-run placeholder carries that stage on the status column: it defaults to the machine start, and `body.stage` sets it. A client record is not read. A user, role, or profile approver must match the principal. A form-field approver or a reporting-level approver is not implemented: the endpoint denies with that reason, and the construct is counted in `migration-report.json` (`approver-field`, `approver-reporting-level`). It is not a silent miss. Schedules run as the application, which is Creator's semantics, and they are job functions with no HTTP route.
- Blueprint transition owners decide who may perform a transition. Owner settings are read from the transition itself, from its `before` section, and from an `owners { }` section. Supported owner kinds: users (`users`/`user`, matched against the caller's login user or user id), roles (`roles`/`role`), profiles (`profiles`/`profile`), and a users field of the record (`field`/`user field`, read from the stored record, so the record's assigned user may transition it). A caller who matches none answers 403 `caller is not an owner of this transition`; a transition with no owner settings is open to any caller who passes the form gates. Not supported, and never guessed: an owner setting that names no kind (`owners = ...`, counted as `blueprint-transition-owner`), a reporting-level owner (`approver-reporting-level`), and a field owner on a field that is not a users field (`approver-field`). Each denies the transition with its reason and is counted in `migration-report.json`. During-phase field settings: a stage's `visible fields`, `hidden fields`, `editable fields` (also `updatable fields`), and `read only fields` apply while a record sits in that stage. The record read leaves out the fields the stored stage does not show and names that stage under `stages`; an edit of a field the stage hides or does not let the user change answers 400 naming the field before any write; the edit screen hides and disables the same fields (the React spec carries them as `stageFields`). A transition's `during` section lists the fields a transition call may set in `body.fields` (`fields`, `editable fields`) and the ones it must fill (`mandatory fields`). Any other field, or a missing mandatory one, answers 400 naming it. A transition with no `during` fields sets none. A listed name that is not a field of the form is dropped and counted (`blueprint-stage-field-unknown`, `blueprint-transition-field-unknown`).
- Submit feedback: a saved add shows the form's `success message` (else `Data Added Successfully!`) and clears the form; a saved edit shows `Data Updated Successfully!`, never the add message. A refusal shows the server's validation text; a failure after the row was written (`wrote: true`) says the record was saved. A report row's Delete asks `Are you sure you want to delete this record?` first, and Cancel sends nothing.
- Reports: list (search, filter, sort, 300-row pages), kanban, calendar, timeline, map, pivot, chart, spreadsheet (inline edit endpoint), summary, and detail when the report has a detail view. Custom actions get a `POST` endpoint. The report query endpoint also answers `op: "aggregate"` — a server-side group-and-fold for chart and pivotchart reports (`body.group` plus `body.measures` of `count`/`sum`/`value`), under the same `authorizeRead` scope and hidden-field rules as the row query, paged `ORDER BY ROWID` and capped at ten pages (`truncated` marks the cap; a dry run folds `body.rows`). A chart whose own criteria did not translate, or an endpoint without the op, falls back to reading rows and folding in the client. Gantt, a kanban with nothing to group, a calendar or timeline with no date, a map with no latitude and longitude, and a pivot or chart with no group are TODO items. No geo column is invented.
- Pages: ZML panels, report and form embeds, charts, gauges, buttons, text, search, and HTML snippets. An unknown tag is a TODO element; its children are still rendered. HTML snippets are parsed with the DOM and rebuilt from an allowlist of tags and attributes. Script, inline event handlers (including slash-separated and entity-encoded ones), `javascript:` and `data:` URLs, `srcdoc`, and CSS `url()` are dropped. Embedded Deluge in a snippet is not executed.
- Server-side Deluge snippets the compiler cannot translate safely stay one counted TODO (`Server-side Deluge snippet requires manual translation`) in `migration-report.json`. An island that writes or calls out on render (`insert into`, `update`, `delete from`, `sendmail`, `invokeUrl`, a `Form[criteria].Field = value` write) is always refused, whatever else it holds. Each such TODO carries reasons from one fixed list, in this order: `write`, `render-navigation`, `caller-read`, `dynamic-url`, `sanitizer-loss`, `untranslated`, plus a manual step that names the snippet and its page. The generated tree writes them to `ui-manual-steps.json` (`{ manualSteps: [{ area, name, reason, reasons, step }] }`, only when there is at least one). `c2c analyze` prints the step on a `step:` line under the UI blocker, and its JSON blocker carries `manualReasons` and `manualStep`. The guidance never clears or reclassifies the TODO.
- Menu sections become the navigation. A hidden section is left out of the nav. A direct hash to a form or report that lives only in a hidden section is posted to the handler that embeds `functions/access-policy.json`, and that handler responds 403. The client does not render the screen.

## Design tokens and visual baseline

`packages/ui/src/tokens.ts` is the one source of the generated app's look: colour roles for a light and a dark scheme, spacing, type scale and font stacks, radius, elevation, motion, and control sizes, plus the shell palettes keyed by the export's `new theme` number. `slate/assets/app.css` begins with those tokens as `--c2c-*` custom properties, and every component rule after them reads colours, shadows, font stacks and type sizes only through those properties. Light applies by default. Dark applies when the page's `<html>` carries `data-color-scheme="dark"`, or `data-color-scheme="auto"` on a device that prefers dark. The generator does not set that attribute yet, so generated apps stay light. Theme palettes keep their menu and accent colours in dark; the light top strip turns dark. Light and dark text pairs are tested at WCAG AA (4.5:1). Motion durations drop to `0s` under `prefers-reduced-motion`.

The same tokens are committed as a standalone stylesheet, `packages/ui/tokens/c2c-tokens.css`: plain CSS custom properties with no build step, so any UI runtime can import it unchanged. `npm run tokens:css` rewrites it from `tokens.ts`, and a test fails when the two drift.

`packages/ui/test/visual-baseline.json` pins the computed styles of key shell, form and report elements for three apps, plus themed and dark variants, at 1440 and 390 px. The test boots the generated shell and runtime in jsdom against a fake data API. It resolves media widths, custom properties and selector specificity itself, so no browser is involved. When a visual change is intended, run `C2C_UPDATE_VISUAL_BASELINE=1 npm test` and review the JSON diff with the change.

`packages/ui/test/visual-pages.json` does the same for the page surfaces: the first list report and the first report with sample rows loaded (table cells, card rows, toolbar and pagination), the first form, each generated report view (kanban, calendar and timeline board lanes; summary, spreadsheet, map and pivot grids), and the first ZML page (layout containers, panels, KPI tiles and embeds) for every app that has one, plus the rail-theme and dark variants of the page-bearing app. Single lengths pass inside half a css px; every other value must match exactly. The same `C2C_UPDATE_VISUAL_BASELINE=1` regenerates it.

## Auth

`packages/auth` writes a dry-run plan: hosted and embedded login both on, public signup off, one Catalyst role per Creator profile, `clone_role` set to `App User` or `App Administrator` (the API requires a clone; the role id is resolved at apply time, not invented here). Portal profiles are app users on the portal role. Nobody is invited. Table permissions are SELECT/INSERT/UPDATE/DELETE from the report verbs and the module `Create` and `Viewall` flags. `Viewall` is GLOBAL scope; other grants are ORG. Creator record filters stay on the access policy `shims/access.ts` already consumes. Hierarchy roles are listed so that allow-list matches the export. They do not receive Data Store permissions unless a profile has the same name.

Field and record security is enforced by the generated `c2c_api`, never only in the client:

- **Fields.** Hidden fields (`visibility:false`) are removed from every read and from write replies; a write that names a hidden or read-only field is refused with 403, not dropped.
- **Create and Edit.** The module `Create` flag allows add; the report `Edit` verb allows edit; `Delete` is its own grant. `Create` with no View and no `Viewall` is an add-only grant: the caller can submit and can read nothing back.
- **Record sharing.** On a portal profile, and on a form listed in `role Hierarchy`, a grant without `Viewall` reads, edits and deletes only the rows the caller added (`Added_User` is the signed-in user's login); `Viewall` without `Modifyall` reads every granted row and edits or deletes only the caller's own. Report record filters are ANDed in as before.
- **Not enforced, listed per app.** `migration-report.json` `security` counts what is enforced and lists every rule that is not as `not enforced: ...`: sharing up the role hierarchy, the Data Store bypass (table permissions carry no field or row rule, so the rules hold only through `c2c_api`), module flags with no generated endpoint (`Tab`, `Export`, `Import`, comment and report-builder flags), report filters that did not migrate (refused instead), and `PIIAccess`/`ePHIAccess` set to false.

A profile with no `ModulePermissions` is not an implicit allow, and it is not left with zero grants when Creator already defined the set. The export stores those predefined sets as the profile name and description, not as module blocks. The generator writes the grant explicitly:

- **Administrator** — app owner and admins. View, add, edit, and delete every form (GLOBAL). This is the default writer. The shim `delete` bit is set.
- **Write** — view, add, and edit every form (ORG). This is a predefined set an App User clone can carry. No delete.
- **Read** — view every form (ORG). No write and no delete.
- **Customer** portal, description "only add and view" — view and add every form (ORG). The shim has one write bit, so add also allows update in `authorizeWrite`. It does not allow delete. Live delete uses `authorizeDelete` (`grant.delete`), not `authorizeWrite`.
- Any other profile with no modules, including **Developer**, gets no table grant.

`App User` and `App Administrator` stay the Catalyst clone targets. They are not extra profile names. A profile that lists modules keeps those modules and does not also receive a predefined grant.

The `ui`/`deploy` trees also carry the apply artifacts under `auth/`: `c2c-auth-apply.json` (every role, permission, scope, and invite op in order), `c2c-auth-apply.md` (the console path for each op), `c2c-auth-apply.mjs` (an optional script that resolves role and table ids through `GET /role`/`GET /table` and sends the captured REST shapes; printing is the default and it never sends an invite), and `c2c_user_validation/` (a Basic I/O Custom User Validation function that denies every signup until the operator fills its allow list; only a planned portal role is assignable). `functions/c2c_api/principal-map.json` maps each generated Catalyst role to its Creator profile so a user on a custom role still resolves a principal.

## Commands

```sh
node dist/cli/src/c2c.js ui path/to/app.ds --out dist/app
node dist/cli/src/c2c.js auth path/to/app.ds
node dist/cli/src/c2c.js ui-corpus path/to/apps --label "local corpus" --out report.md
node dist/cli/src/c2c.js score-ui path/to/app.ds --ui dist/app
```

`score-ui` is a maintainer and CI tool: it scores the generated UI against the Creator source on a desktop and a phone viewport, out of 10 each, offline in jsdom (a dev dependency). The rubric and the local-corpus scores are in [ui-scores.md](ui-scores.md).

`ui` writes `slate/` (the static app), `functions/` (Advanced I/O), and `client/` (the Deluge client modules). `auth` prints the plan. Neither command contacts Catalyst.

Submit and report writes and queries run only when `functions/c2c-deploy.json` has `"mode": "live"` and a datastore adapter is installed. The generated mode is `"dry-run"`, which checks access and returns no rows and no insert. Uploads and lookups stay dry-run in either mode.

A report custom action whose workflow names, exactly (case-sensitive), a `type = functions` workflow with `execution type = for each record` or `collection of records` that generated (`functions/custom/<slug>.mjs`, registered in `functions/thisapp.mjs`) runs live: the endpoint dispatches the function in-process through that registry, and its field writes persist. A record-bound function (`execution type = for each record` or `collection of records`) runs on the row whose `ROWID` the client posts; no `ROWID` is an empty selection, answered 200 `wrote: false` with nothing run. The row is read under the caller's policy (a row the caller cannot read is 404) and must also be the caller's to modify: a View All grant without Modify All gets 403 on another user's row, and the function does not run. In any mode but `"live"` the endpoint answers the dry-run preview. An action whose workflow generated no such function (no match, a case-different name, a standalone Deluge function, or a workflow without a record execution type) has an endpoint that runs nothing (a live call is refused with 422): both clients draw its button turned off with a note naming it ("Not available yet, so turned off: …"), and each such action is a counted TODO in the migration report; a click never reports a run. The endpoint and the button read the same predicate, so a button is enabled exactly when its endpoint can run. A live request with no adapter returns 500 and does not call the network.
