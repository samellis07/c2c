# Creator field type → Catalyst schema

One row per field type the schema generator maps. The reason is the contract, not a hint.

For a field stored as one column, Creator `must have` and `unique` are emitted as `mandatory` and `unique`, and `initial value` is emitted as `defaultValue` when Catalyst supports a default for that column type. Text, Foreign Key, and Encrypted columns keep their documented default behavior: no Catalyst default, with a generated-form prefill warning. Type-specific size, precision, lookup relation, and composite parts are described in the row reason. Source-measured constraint demotions and the per-table unique-varchar limit are described below.

## Decisions

- **currency.** Currency, decimal, and percent are an exact canonical decimal string in VarChar length 64, not Double and not bigint minor units. Decimal is not a Catalyst column type. Scale is the field decimal places (default 2). Extra fractional digits quantize half-away-from-zero. The currency ISO code is field metadata. Percent is the typed number, not divided by 100. ZCQL orders the varchar lexicographically; numeric order is the generated comparator.
- **varchar.** VarChar longer than 255, or a choice longer than 255, is promoted to Text. Inserts are never planned around silent truncation.
- **fk.** Lookup single is data_type "foreign key" with on_delete ON-DELETE-SET-NULL when the field is optional and ON-DELETE-CASCADE when it is mandatory. The parent column is ROWID. A missing target is a bigint id and the report item "FK needs console".
- **nosql.** Data Store is the default. Every inline subform (type = grid with nested fields) is a child table with parent_id ON-DELETE-CASCADE and row_order, however many subforms the form has. The schema step does not plan NoSQL collections.
- **signals.** Each Data Store table gets three Signals rules, one event per rule: row_inserted, row_updated, row_deleted. Targets are Event functions only. NoSQL collections are not Data Store row events.
- **jobPool.** Job pool names cannot contain "_". This plan does not create job pools.
- **sourceId.** Every migrated table, including child and junction tables, has a varchar c2c_source_id (255) holding the Creator record id. It is not mandatory and not unique: rows the deployed app creates leave it NULL (a mandatory column fails every app insert with 403 MANDATORY_MISSING), and a unique varchar would spend the per-table unique varchar budget. The loader enforces one row per Creator id: it refuses a source that repeats an id, and the server-side write gate never accepts c2c_source_id from a client. A field that would have used that name is renamed. Creator v2.1 Get Records returns ID as a numeric string; the published sample is 17 digits and a lookup criteria example is 19 digits. The mover rejects a longer source id before insert instead of hashing it, because a varchar past 255 is stored truncated. It reconciles a pending batch with ZCQL IN queries of at most 300 ids and skips ids already stored. A DUPLICATE_VALUE response (HTTP 409) re-queries that batch, drops ids now present, and retries the rest; any other write error fails closed. It does not upsert. Each live table run holds a checkpoint lease (owner id and expiry, renewed on each save, released when the table finishes or the run throws). Another mover does not write that table while the lease is unexpired; an expired lease can be taken over. Movers that do not share the checkpoint rely on the re-reconcile on resume.
- **uniqueVarchar.** Data Store refuses a third unique varchar column on one table (403 INVALID_OPERATION "Reached max number of columns of Unique varchar type"). The schema keeps the first UNIQUE_VARCHAR_MAX_PER_TABLE unique varchar columns of a table, in field order, as store-level unique. The rest are created not unique and marked appUnique: the generated handler checks them with a ZCQL read before insert and update and refuses a duplicate. That check is not atomic, so two concurrent submits can both pass. A unique varchar the source data disproved also demotes (see constraintsFromSource) and frees its slot for the next unique column. precheck reports every table over the budget.
- **uniqueDate.** A unique date or datetime column refuses EVERY insert with 400 INVALID_INPUT "date value expected" — the same value a non-unique date column accepts [TESTED 2026-10-16]. The schema therefore never sets is_unique on a Date or DateTime column: a Creator "no duplicate values" date field is created not unique and marked appUnique, and the generated handler enforces it with a ZCQL read before insert and update. That check is not atomic, so two concurrent submits can both pass; Data Store-level uniqueness is not enforced for dates. The demotion does not depend on source rows.
- **constraintsFromSource.** With source rows to measure (a backup, an export, or a seed), a store constraint is kept unless the data itself disproves it: a Creator "must have" field demotes only when a row carries the column with an empty value, and a "unique" field demotes only when two carried non-empty values repeat. A disproved constraint demotes to the app layer — the column is provisioned without it and the schema marks it appMandatory or appUnique — and the generated app enforces the Creator rule instead: an insert or update carrying an empty value is refused MANDATORY_MISSING, and an app-unique value is checked by a ZCQL read before insert and update. Existing rows that violate the flag still load: Creator applies the flag at submit time, not retroactively. Every demotion is a plan decision {table, column, rule, layer: "app", violations} named in the plan and fidelity output with the offending row count, so re-runs, the table templates, and provisioning agree. A field the source does not carry proves nothing — the store constraint stands (a complete source may store the field outside the row files, as a backup's reverse-lookup rel# files do), and a load that leaves a kept is_mandatory column empty, or repeats a kept store-unique value, is refused before any write with the column named and a re-provision instruction. Confirmed loads check against the constraint flags the live project actually reports — the provisioned decisions replayed onto the generated schema — not a re-measure of the current input. Generated columns (c2c_source_id, system fields, parent links) are never demoted this way.
- **logicalId.** Creator `ID` is a logical field; generated tables have no ID column. A migrated row keeps its Creator id in c2c_source_id; an app-created row has only ROWID. A Deluge criteria on `ID` compiles against both — `ID == x` and `ID in (…)` become `(c2c_source_id IS NOT NULL AND c2c_source_id = x) OR ROWID = x`, `!=` becomes `(c2c_source_id IS NULL OR c2c_source_id != x) AND ROWID != x`, and ordering/text leaves compare the row's effective id (c2c_source_id when set, else ROWID). Ordering is numeric, as in Creator: c2c_source_id is a varchar that ZCQL compares as text and ZCQL allows no function or CAST in WHERE, so a digit operand compiles to digit count first (a LIKE with ZCQL's `?` one-character and `*` any-run wildcards), then text order within the same count — numeric for ids without leading zeros, so a 17-digit id sorts before a 19-digit one. The in-memory matcher uses the same order on both arms. Every leaf is total (never UNKNOWN) so it composes under AND/OR/NOT. A criteria value may be a number, digit string, bigint, or a lookup `{id,label}` — the id is unwrapped and compared exactly, never through `Number()` (see ids.ts). A lookup-field cell already stores the target ROWID (the FK remap rewrites it), so `Form[ID == rec.Lookup]` resolves by ROWID. Reads of `rec.ID`, `input.ID`, `old.ID`, `Form[criteria].ID`, `distinct(ID)`, and `sort by ID` resolve to the Catalyst ROWID — not the source id — so an id a script stores and later queries by `ID` always round-trips.
- **systemFields.** Every form table and inline-subform child table has Added_User, Added_Time, Modified_User, and Modified_Time. Added_User and Modified_User are varchar 255 and store the Creator username. Added_Time and Modified_Time are datetime. They are not mandatory and not unique. A form field that would have used one of those names is renamed. Junction tables do not get these columns. The mover and the CSV import copy the values from the source row and do not stamp the signed-in user or the current time. Creator v2.1 Get Records returns the visible fields of the report (https://www.zoho.com/creator/help/api/v2.1/get-records.html). The published all-field-types sample does not include Added_User, Added_Time, Modified_User, or Modified_Time on the record. When a source row omits them, the column is left empty and the run records a system-field coverage gap. It does not invent a value.
- **bidirectionalRel.** A bidirectional lookup stores the link once, on the forward side: a backup's rel#<field>#<form>.csv carries the forward rows, and the reverse column on the target form has no cell in the basic# files. The loader fills the named reverse column on each target row with the base record id, single and multi alike, and remaps it to the Catalyst ROWID like every other lookup. A reverse column the basic# files do not carry is therefore populated, never empty, and is not a constraint violation.

`.ds` tokens and matrix names share a row. `type = INR` (any ISO 4217 code) is Currency.
A `checkbox` with a choice list or a lookup is Checkbox (multi), not Decision box.
`values = Form.Field` on a single-value field is Lookup single; on list/checkboxes it is Lookup multi.

| Number | `number` | supported | column / BigInt | Bigint (19 digits), not int (10). Data Store returns bigint as text; the datastore adapter reads it as a JS number (a JS bigint past 2^53, so no digit is lost) and writes it back as the same digits, so generated arithmetic adds instead of joining text. |
| Decimal | `decimal` | partial | column / VarChar | Decimal is not a Data Store column type (Text, VarChar, Date, DateTime, Int, Double, Boolean, BigInt, Foreign Key, Encrypted).
