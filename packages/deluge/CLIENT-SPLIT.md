# Client / server split

A client action (`alert`, `info`, `openUrl`, `cancel submit`, show / hide / enable / disable, field `:ui`) sometimes sits under a condition or loop that reads the data store, `zoho.*`, or `thisapp.*`. The browser cannot run that read. The generator does not drop the action and does not leave it as `client-condition-uses-server` / `client-loop-uses-server` when a snapshot is enough.

## Rule

1. Each server-only expression the client must see becomes one **prefetch slot**. The generated Advanced I/O endpoint `POST /forms/<form>/<event>/prefetch` (or `POST /functions/<name>/prefetch`) evaluates those expressions and returns `{ slots }`. It replays the server locals the expressions read, once each, in assignment order — a local bound by a read-only expression (a literal, arithmetic, an environment read such as `zoho.loginuser` or `zoho.currentdate`, or a query that touches neither the current row nor an unbound local) replays, and a self-assigned scalar (`n = n + 1`) replays as its previous binding followed by the self-assign. It does not replay inserts, updates, deletes, mail, an outbound HTTP call (`invokeurl`, `getUrl`), an integration task, or a same-app function call: a binding holding one stays a counted `client-condition-uses-server` / `client-loop-uses-server`, because the prefetch would run the effect a second time. A read replays the binding that was in force when its assignment ran, so a copied local sees the value it captured (`n = 1; limit = n; n = n + 9` replays `limit` against `n = 1`), and one expression needing two versions of a name gets both, emitted in assignment order. A binding assigned where it may not have run — an `if`/`else` arm, a loop body, a `try`/`catch` arm, or a function body — does not dominate a later use and is never replayed: the read stays a counted todo. An `if` or `else if` test and a `for each` collection are slotted against the bindings in force at that test or collection, so an assignment inside an arm or the loop body does not hide a value that dominates it. A name assigned anywhere in a `for each` or `while` body is not one value for a read of that name inside the body — the prefetch would repeat a single iteration — so the read stays a counted todo. A `while` test is evaluated on every iteration, so a body assignment of a name the test reads stays a counted todo as well.
2. The client handler calls `shim.client.prefetch(ctx, path)` **once, at the start of that handler** — form load for an `on load` script, and the same moment the handler runs for user input or validate. The condition then runs in the browser against the slot.
3. **`if` / `else if`.** The whole test is one boolean slot when it does not also read the current `for each` row. The slot uses the bindings from before the arms, not an assignment inside the then, else-if, or else arm. A read inside a later arm uses those same bindings: an earlier arm has not run. A name any arm assigns does not dominate a use after the `if`, and it stays client-ready only when every arm — and the fall-through path when there is no `else` — leaves it the same kind. When the paths disagree (one bound a side effect, a query, or another value the client cannot reproduce), a later read stays a counted todo rather than silently evaluating the last arm's kind. The server handler, if it has server statements, still evaluates the test itself when it runs.
4. **`for each`.** Deluge evaluates the collection once, then iterates. The prefetch slot is that collection (rows, when the collection is a query), using the bindings from before the body. The client loops over the snapshot. The loop variable is ordinary client data, so a nested `if (rec.Field == …)` runs in the browser. A ranged fetch (`range from … to …`) whose bounds dominate before the loop snapshots only the page the range names; if the loop body moves the page window, no later page is read — the emitted client loop carries a `snapshot` comment saying so. A range bound that reads a pure local an earlier client loop wrote is not that snapshot: the client evaluates the bound and posts it (`shim.client.rows`), and the endpoint clamps the integers and runs the one compiled query for that slot. A bound assigned in an `if` / `else` arm stays a counted `client-loop-uses-server`. A read inside the body of a name the body assigns stays a counted todo, as does a read of a name no assignment ever bound — the prefetch would otherwise emit a dangling reference.
5. **`while`.** The client cannot re-query, and `while (frozenTrue)` would not terminate when the body is only client actions. The test is snapshotted once and the client body runs **at most once** (`if (slot)`, with a `snapshot` comment) when the body does not assign a name the test reads. A test that reads a name the body assigns stays a counted todo, as does a read of that name inside the body. The server keeps a real `while` when the body has server statements.
6. **Row map.** An expression that reads the current prefetched row and another server value is computed on the server for each row already fetched for that loop. The prefetch returns one map keyed by the row's `ID`. The browser indexes the map with the current row. It is still one prefetch call, and the endpoint uses the same profile, field allow-list, and record filter as any other slot. A key the map does not have is null, the same as `Form[criteria].Field` when no record matches (`shim.datastore.field`). A missing collection is null, and `for each` over null runs zero times (`shim.each`). A local that is not a prefetched row still stays `client-condition-uses-server` or `client-loop-uses-server`.
7. **Per-element round trip.** A `for each` over a non-record server collection (a `getAll` column) still gives the client a snapshot to iterate. A condition inside that loop that reads the element *and* another live server value cannot be one load-time slot — but the element itself is client data the client can send back. The client POSTs `{ element: { name, value } }` to the same prefetch endpoint, one round trip per element, and the endpoint evaluates just that element's slots (`ctx.element` names which loop variable the value is for; guarded `if` blocks skip every other element's slots and run nothing in the one-shot prefetch). The round trip carries the same nonce, caller, and read policy as the load-time prefetch. The endpoint only evaluates allowlisted read shims (`datastore` reads, `record.get`, `input.get`, pure helpers): a condition or replayed binding that calls a same-app function (`thisapp.*`), a write (`insert`/`update`/`delete`/`setField`), mail, or http stays the counted `client-condition-uses-server` todo and emits no element slot; a `thisapp.*` collection itself cannot be snapshotted, so such a loop stays a `client-loop-uses-server` todo. The posted value must be a scalar member of the iterated collection — a non-member or an element past `LIMITS.clientElementRoundTrips` (100) is refused server-side with nothing evaluated. A slot that evaluates to a dry-run placeholder is reported as `{ ok: false }`, never truthy. A refused, stale, placeholder, or over-cap round trip throws `c2cElementBlocked`: the handler run discards every client action it already queued, so a mid-loop failure never leaves partial actions applied. A record element (a fetched row) stays on the row path.

Dry-run `shim.client.prefetch` does not invent slots. With no adapter it returns `{ ok: false, slots: {} }` and records `client-prefetch` with `performed: false`. An injected `clientPrefetch` adapter is the server round-trip. It is called with the form-state nonce and must echo `{ slots, nonce }`.

## Authorization

The prefetch endpoint and the server handler that reads the same records use one policy (`access` on the runtime):

- The caller is `principalFromRequest`. That reads the platform user (`req.user` or `req.catalyst.user`). A profile on the request body is ignored.
- No authenticated profile is HTTP 401 and no slots.
- Table permission is the profile's module grant. A form the profile cannot view is HTTP 403. Nothing is returned for that form — not an empty row set.
- Field permission drops every field the profile cannot read (`visibility` false, or not on the allow-list). A read of a hidden field is 403.
- Record permission is the Creator report the profile can `View`. `show all rows from Form [criteria]` is ANDed onto the query. Several such reports are OR-ed. A report with no criteria, or `Viewall`, does not add a filter. A filter that mentions `zoho.loginuser` / `zoho.loginuserid` is bound to the principal, not to a value the client sends. A filter that cannot be compiled denies the read.

## Stale responses

`shim.client.touch(ctx)` sets a new nonce on form load and on each field change. The generated client does that before prefetch. The endpoint echoes the nonce it computed for. The client acts on the slots only when `ok` is true and the nonce is still the current form nonce.

A stale response (the form changed while the request was in flight, or the nonce does not match) or a failed response is discarded. The shim makes one more server round-trip with the current nonce. If that also fails or is stale, the client pushes an `info` action with the message and returns without running the condition. An empty slot list is not treated as a false condition.

## Conversions

`toLong` (alias `toNumber`), `toDecimal`, `toList`, and `toMap` are shim calls, not TODOs. Semantics and the throw-on-empty / throw-on-invalid rules are in `packages/shims/src/convert.ts`, cited from the Deluge help pages. `toString`, `toDate`, and `toTime` were already translated.
